\subsection{Entwicklungsumgebung}

% [X] C++, CMAKE
% [X] Testbasierte Entwicklung
Die Bibliothek wurde in C++ mit Visual Studio Code als integrierte Entwicklungsumgebung entwickelt. Zusätzlich war CMake durchaus eingesetzt, um das \textit{Packaging} der sämtlichen Modulen durchzuführen. Für alle Modulen wurde testgetriebene Entwicklung eingesetzt, um sicherzustellen, dass alle funktionelle  und nicht-funktionelle Anforderungen abgedeckt werden. Darüber hinaus wurden beide \textit{google-test} und \textit{google-mock }für die Realisierung von Testfällen angewendet.

% [X] Docker

Für die Ausführung der Testszenarien sind eine Kombination aus Docker und Simulink verwendet worden, unter Verwendung der von BaSyx veröffentlichen \textit{Docker-Containers} für den \textit{Registry}- und \textit{AAS}-Server für die Bereitstellung der BaSyx-Architektur eingesetzt wurden. Außerdem wurden die Verwaltungsschalen mittels \textit{AASX Package Explorer} erstellt, eine Open-Source-Software zur grafischen Visualisierung und Bearbeitung von \textit{AAS/Submodel/SubmodelElements}.
\subsection{Wrappen des BaSyx als S-Funktion}

% [X] Funktionweise des BasyxConnectors und wie es mit dem Block verbunden ist

Der \textit{BasyxConnector} wird innerhalb eines Blockes direkt aufgerufen, um Operationen wie einen AAS aus dem Registry-Server abzurufen und den Wert eines \textit{SubmodelElements} anzufragen, bzw. aktualisieren.

Eine Öffnung der Klasse \textit{aasServerConnector} zeigt auf, dass diese im Konstruktor beide ein Objekt des Typs \textit{AAS} und \textit{HttpConnection} erfordert. Zum Aufbau eines AAS-Objekts wird es auf die Datei \textit{components.hpp} verwiesen, wobei eine neue Instanz entweder aus der Klasse \textit{registryServerConnector} über die Methode \textit{fetchAAS(...)} ausgegeben oder anhand der ID und URL-Pfades erstellt werden kann. 

Ein \textit{HttpConnection}-Objekt kann über eine der Implementierungen der Schnittstelle \textit{httpConnection.hpp} angelegt werden. Diese dient zu dem Tätigen von HTTP-Anfragen, wodurch eine effektive Entkopplung von deren  Ausführung und dem \textit{BasyxConnector} erreicht wird. Momentan wurde nur eine Implementierung (\textit{curlHttpConnection}) über die externe Bibliothek \textit{libcurl} realisiert.

% [X] Übersicht von den Config-Datei und die benötigten APIs-Pfade usw
Um eine Änderung der fest codierten API-Pfaden leichter vorzunehmen, wurden alle API-Pfaden in einer einzigen Datei (Code \ref{code:BasyxConfig}) eingefügt, auf die die sämtlichen Methoden der Bibliothek zugreifen können.

Innerhalb der Datei \textit{PropertySAConnectorBlock.cpp} findet sich die Logik, eine Verbindung mit beiden \textit{BaSyx} und \textit{Simulink} herzustellen. Die Klasse \textit{CurlHttpConnection} wird als Zeiger instanziiert, und als Argument zur Erstellung von Objekten des Paketes \textit{BasyxConnector} über die Methoden \textit{mdlStart und mdlOutputs} verwendet. 

% [X] Anwendung dieser komischen Vektoren Simulinks, um das Problem von static Parameters umzugehen wird

Um globale Variablen innerhalb der \textit{Simstruc}-Umgebung zu realisieren, werden \textit{Work} Vektoren benötigt. Mit diesen lässt sich Zustand innerhalb einer Block-Instanz speichern und dadurch Initialisierungsparameter wie \textit{aasId, registryUrl, submodelElementId} unter anderen beibehalten werden.
Dafür werden hauptsächlich zwei \textit{simstruct}-Methoden eingesetzt, nämlich \textit{ssGetPWork}, \textit{ssGetPWorkValue}. Die erstere dient zur Bearbeitung des \textit{Work} Vektors, während die letztere zum Ablesen eines in diesem gespeicherten Wert.

Im Codeauszug \ref{code:propertysaconnectorblock} lassen sich Beispiele für die Anwendung von \textit{Work} Vektors entnehmen, in dem diese zunächst über die Methode \textit{initializePVectors} initialisiert und später bei jedem Lesevorgang verwendet werden, mit dem Ziel die \textit{AAS}, \textit{Submodel} und \textit{SubmodelElement} Objekten abzurufen.

% [X] Wie ein Durchlauf aussieht

Die Methode \textit{mdlStart} wird am Moment der Instantiierung des Blockes aufgerufen. Somit werden Objekten wie \textit{AAS, Submodel und SubmodelElement} angelegt und im internen Zustand über einen \textit{work} Vektor gespeichert.
In jedem Simulationsschritt wird die Ausgabe über \textit{mdlOutputs} berechnet. An dem Moment unterscheidet \textit{PropertySAConnectorBlock}, ob eine Verbindung am Eingang, am Ausgang oder an beiden Ports liegt. Je nach Fall wird an den \textit{BasyxConnector} eine Aktualisierungs-, bzw. Leseanfrage übersendet. (s. Code \ref{code:propertysaconnectorblock2})

\begin{codeblock}{cpp}{propertysaconnectorblock2}{Auszug der PropertySAConnectorBlock.cpp Datei}

    {    
        const double* u = (const double*)ssGetInputPortRealSignal(S, 0);
        double       *y = ssGetOutputPortRealSignal(S,0);
        try{
          // Case snapshot mode
          if(getNumPar(S,PAR_BM)==0){

            return;

\subsection{\ref{req:A10} Ablesen des Wertes aus einem \textit{SubmodelElement}}

% [X] Übersicht von dem Diagramm unten
Für das Ableseverfahren wird es vorausgesetzt, dass eine Verbindung an dem Blockausgang vorliegt. Die Methode \textit{mdlOutputs} wird ausgeführt, und infolgedessen die Methode \textit{getSeValue} des \textit{BasyxConnector} aufgerufen wird. Dieser erzeugt wiederum eine formatierte URL für den \textit{HttpClient}. Anschließend stellt der \textit{HttpClient} eine GET-Anfrage an dem \textit{BaSyx-Server}, und somit dessen Antwort vom \textit{HttpClient} in einem \textit{Struct} mit expliziten Parametern für die rohe Antwort und den \textit{Status-Code} umgewandelt wird (s. Code \ref{code:propertysaconnectorblock3})

        AasServerConnector aasCon = AasServerConnector(*aas, *httpCon);
        return  std::stod(aasCon.getSeValue(*se));
    }
    ...

    // aasServerConnector.cpp
    ...
    string AasServerConnector::getSeValue(SubmodelElement &se)
    {

        if(resp.httpCode != 200 )
            throw std::runtime_error("Unable to get SubmodelElement value at '"+aas_.aasUrl.getStr()+"'");

        ...

\subsection{\ref{req:A30} Abrufen von AAS-Daten aus einem Registry Server}

% [X] Übersicht von dem Diagramm unten

Im Gegensatz zu dem Ableseverfahren des Wertes eines \textit{SubmodelElement} wird die Logik für das Abrufen eines AAS-Datensatzes in der Methode \textit{mdlStart} (über die Methode \textit{initializePVectors}) ausgeführt und anschließend wird die formatierte URL über die Methode \textit{fetchAAS} vom \textit{BasyxConnector} erzeugt. Der URL wird am \textit{HttpClient} überreicht, wobei aus der Komponente eine GET-Anfrage an dem \textit{BaSyx}-Server gestellt wird. Die davon erhaltene Antwort ist am Ende vom \textit{BasyxConnector} abgewickelt, und ein Objekt des Typs \textit{AAS} wird am Block zurückgegeben. Der Prozess ist in der Abb. \ref{fig:C30} veranschaulicht und einen Auszug der Implementierung kann im Codeauszug \ref{code:createaas} gefunden werden. 

\begin{codeblock}{cpp}{createaas}{Auszug der PropertySAConnectorBlock.cpp Datei}
// PropertySAConnectorBlock.cpp
...
static Aas createAas(string aasUrlStr, string regUrlStr, string aasId){
  // Create AAS based on whether user has provided an AasUrlStr or not
  if(aasUrlStr == ""){
    Url urlStr = Url(regUrlStr);
    RegistryServerConnector regCon = RegistryServerConnector(std::move(urlStr), *httpCon);
    return Aas(regCon.fetchAAS(aasId));
  }else{
    Url urlStr= Url(aasUrlStr);
    return Aas(urlStr, aasId);
  }
}

\subsection{\ref{req:A40} Anzeigen von Simulink-konformen Fehlermeldungen} \label{ProzessA4}

Wäre ein Status-Code nicht gleich 200 erhalten, löst der \textit{BasyxConnector} eine Ausnahme mit Details des empfangenen Paketes aus, die weiterhin an den entsprechenden Block zugeleitet wird. Für das Wrappen der Ausnahme wird eine Simulink-konforme Methode angewandt, durch die Fehlermeldungen direkt im Simulink-Konsole angezeigt werden können. Das Abbild \ref{fig:consolefehler} stellt ein Beispiel einer Fehlermeldung, bei der der Server nicht in der Lage war, mit dem Registry-Server eine Verbindung herzustellen.

Eine globale Variable ist deshalb mit allen anderen Blöcken gleiches Typs geteilt, was ein Problem für die Beibehaltung der Daten unter Simulationsschritten darstellt. Wie bereits erwähnt, können zur Umgehung dieses Problems und um den Blöcken einen internen Zustand zu verleihen, \textit{work}-Vektoren verwendet werden.

\subsection{\ref{req:A60} Betriebsmodus wechseln}

% [X] Betriebsmodus wechseln
Der Betriebsmodus ist als Parameter im Simulink eingegeben, und anschließend in den \textit{mdlStart, mdlOutputs und mdlTerminate} Methoden in \textit{"PropertySABlockConnector.cpp"} geprüft und implementiert. Beim Einschalten vom Abbild-Modus wird die Daten des \textit{Submodelelement} nur beim Aufruf vom \textit{mdlStart} und \textit{mdlTerminate} abgerufen, während dies im Echtzeitmodus bei jedem Aufruf von \textit{mdlOutput} geschieht.

\subsection{\ref{req:A70} Personalisierung der Blockbenutzeroberfläche} \label{Simulationsumgebung}

Wie im Kapitel \ref{BenutzeroberflaecheSimulink} kurz erläutert, bietet Simulink mehrere Möglichkeiten der Benutzeroberfläche eines Blockes zu personalisieren. 

Bei beiden Blöcken war es eine kritische Anforderung, dass alle einzustellenden Parameter gut erkennbar waren, um schnell von mehrfachen eingefügten Blöcken zu unterscheiden.

% [X] Bilder von Blöckenbenutzeroberflächen
% [X] Beschreibung der Bilder
Das Block-Symbol wurde personalisiert, um schnell einen Überblick der eingestellten Parameter zu bekommen. Dazu sind Informationen wie die Abtastrate und das verbundene \textit{SubmodelElement} und dessen \textit{Submodel}, bzw. \textit{AAS} immer sichtbar, wie im Bild \ref{fig:sesab_block} dargestellt ist. Das ermöglicht die schnelle Erkennung und Unterscheidung von mehrfach eingefügten Blöcken in einem Modell.


\img{5cm}{media/SeSAB_block.jpg}{sesab_block}{Instanz eines PropertySAConnector-Block}



Nach Tippen auf einen Block wird dem Benutzer ein Dialogfenster mit Textfelder für alle einzustellende Parameter angezeigt. Das wurde erst durch die Erstellung einer Maske für die \textit{S-function}, eine im Simulink eingebettete Funktionalität. Die Abb. \ref{fig:sesab_dialog} zeigt ein Beispiel einer Instanz des Blockes \textit{PropertySAConnectorBlock}.


\img{10cm}{media/SeSAB_dialog.jpg}{sesab_dialog}{Dialogfenster des PropertySAConnector-Block}



Der Benutzer kann über das Fenster den gewünschten Betriebsmodus auswählen, wobei bei Wählen des Echtzeitmodus das Feld zur Einstellung der Abtastrate sichtbar wird. Es steht jedoch zur Verfügung, die Option auszuwählen, ob es die \textit{AAS} über den \textit{RegistryServer} oder direkt über seine Adresse abgerufen werden soll.
